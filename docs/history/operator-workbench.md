# FIDB operator workbench, batch operations, and toolchain management

Status: design notes; intentionally untracked
Date: 2026-08-25

## Purpose

Build a small operator workbench around FIDB generation and matching. It should expose reviewed settings, recipes, build routes, resolved cells, batch progress, evidence, and automation controls without becoming a second source of build truth.

The workbench should help an operator answer four questions quickly:

1. What is planned, running, complete, or blocked?
2. Exactly what reviewed inputs and route will each cell use?
3. When is this batch or campaign likely to finish?
4. Are all required toolchains and execution dependencies ready?

This is operational infrastructure, not a generic settings page.

## Relationship to BSimVis

BSimVis is best treated as the downstream analyst workspace. Its useful interaction patterns include:

- a persistent navigation sidebar;
- modular views rather than a single long page;
- hierarchical jobs with status, progress, logs, and retry actions;
- upload and import forms with clear validation;
- consistent status badges;
- an API-driven frontend;
- graph, clustering, tagging, and notes for post-build analysis.

The FIDB workbench should use a visually compatible design where practical, but remain a separate control plane. BSimVis should not become the authority for QEMU, local execution, toolchain pins, recipes, or FID build configuration. A later handoff can open completed FIDBs or analysis jobs in BSimVis.

Patterns to avoid carrying over are a monolithic dashboard controller, widespread inline styles, UI state acting as authoritative configuration, and early coupling to Redis/Kvrocks before the workload requires it.

## Operating model

The visible hierarchy is:

```text
Campaign
  Batch
    Item
      Cell
        Stage
```

- A **campaign** is an operational objective, often an overnight or recurring run.
- A **batch** groups related requested outputs.
- An **item** is a requested library, binary, or recipe target.
- A **cell** is one immutable resolved build or match operation.
- A **stage** is a measurable unit such as acquire, prepare, build, Ghidra, match, or export.

Configuration moves in one direction:

```text
Reviewed catalogs
  -> runtime selections
  -> immutable resolved plan and cells
  -> explicit execution
  -> evidence, manifests, reports, and artifacts
```

The browser must not be the process that owns execution. A persistent service on `reference-host` should own schedules, queues, workers, event recording, cancellation, recovery, timing history, and the run ledger. Closing the browser must not stop an overnight job.

## Sources of truth

The UI should read and explain the existing reviewed sources rather than duplicate them:

| Concern | Authority |
| --- | --- |
| routes, treatments, profiles, native tool commands | `worker.json` |
| native recipes | `recipes/*.toml` |
| source library recipes | `recipes/libs/*.toml` |
| malware recipes | `recipes/malware/*.toml` |
| cross-toolchain pins and target ABIs | `toolchains/registry.toml` |
| executor selection | explicit runtime choice, defaulting to QEMU |
| resolved cells | generated by the current Python resolution path |
| build evidence | manifests, hunt reports, FIDBs, checksums, and logs |

Recipes and callers must never supply a raw build command. Both QEMU and local source execution continue to use the same reviewed named build adapter and fixed command construction. Derived commands may be displayed read-only for diagnosis.

## Proposed views

### Overview

The landing view should show:

- system doctor status and detected Ghidra identity;
- QEMU and local executor readiness;
- recipe, toolchain, route, and treatment counts;
- toolchain requirements that are ready, cold, or blocked;
- active campaigns and batches;
- recent failures and their failing stage;
- recent completed artifacts and evidence;
- queue depth, running cells, throughput, ETA range, and free disk.

### Build planner

The planner should guide the operator through native, hunt, and malware workflows. Each choice should constrain the next choice to valid catalog values.

Before execution it displays the exact resolved cells, including:

- recipe and source archive pins;
- toolchain registry row and target ABI;
- named build adapter and compiler flags;
- route, treatment, and profile;
- executor (`qemu` or explicit `local`);
- expected artifacts;
- requirement/readiness result;
- plan digest.

Archive-only hunt candidates should be shown as archive candidates and must not acquire an executor dependency merely because source candidates in the same hunt use one.

### Catalog

Catalog sections should cover native recipes, source libraries, malware recipes, toolchains, routes, treatments, and profiles. Detail pages should expose pins, ABI, adapters, patches, compatible toolchains, consumers, and derived cells.

The first release should be read-only. Later catalog editing should create a proposed TOML diff for review; it should not mutate runtime state invisibly.

### Runs and batches

A batch page should combine:

- a batch table with item/cell status;
- a pipeline tree showing the active stage of every cell;
- a compact timeline or Gantt view;
- duration, worker, executor, inputs, outputs, and error details;
- live logs with stable stage boundaries;
- retry of typed operations where safe;
- filters for status, architecture, toolchain family, executor, adapter, route, treatment, and failure stage.

### Evidence

Evidence pages should make manifests, hunt reports, checksums, logs, and resulting FIDBs easy to inspect and compare. A particularly useful comparison is the same resolved build inputs executed through QEMU and local routes, with the executor difference visible in provenance.

### Toolchains

Toolchain management deserves a first-class view rather than being hidden in a doctor screen. It should show the difference between what exists, what is required by the current plan, and what is usable by each executor.

A matrix should include:

| Field | Meaning |
| --- | --- |
| variant | stable registry identity |
| family/version | reviewed compiler family and release |
| target ABI | machine, ELF class, endianness, and cross architecture |
| capability | archive-only, source-capable, or both |
| state | missing, cached, ready, incompatible, or broken |
| pin | expected URL and SHA-256 identity |
| compiler | expected cross-prefix and detected compiler path |
| executor compatibility | QEMU ready and/or local-host ready |
| consumers | recipes and planned cells that require it |
| cache footprint | archive and extracted sizes |
| verification | last result and timestamp |

Normal actions must be typed: **verify**, **download pinned archive**, **prepare**, **diagnose**, and **remove cached copy** with confirmation. There should be no general command field and no normal workflow for browsing to an arbitrary compiler.

## Toolchain inventory model

“Installed” is not one binary condition. The inventory should distinguish these layers:

1. **Native host tools** — exact configured paths such as the compiler, archiver, and ranlib used by the existing native route.
2. **Pinned archive cache** — the exact cross-toolchain archive exists and its SHA-256 matches the registry.
3. **Prepared cross-toolchain** — the verified archive has been extracted into a managed location and the expected prefix/compiler exists.
4. **Executor dependencies** — QEMU, KVM access, VM image/ISO pins, shell/build utilities, and host compatibility needed to invoke the prepared toolchain.
5. **Analysis dependencies** — Ghidra, Java, PyGhidra, and language mapping required after compilation.

The current native zlib/bzip2 path must remain unchanged. Inventory detection may report its configured tools, but toolchain management must not redirect that route through the new source executor machinery.

Cross-toolchain detection is also not permission to substitute an arbitrary installed compiler. A detected compiler is usable only when it is tied back to the reviewed registry identity and expected target ABI. The registry URL, digest, prefix, and variant remain authoritative.

### Suggested states

- `unknown` — not yet inspected;
- `missing` — no matching cached or prepared copy exists;
- `available-unverified` — something exists at an expected location but has not passed verification;
- `verified-cached` — pinned archive digest matches, but it is not prepared;
- `ready` — expected compiler exists and identity/ABI checks pass in the selected executor;
- `incompatible` — verified toolchain exists but cannot execute in this host/executor environment;
- `broken` — corrupt extraction, identity mismatch, or a failed health check.

Inventory records should capture:

- registry family, version, and variant;
- archive/source capabilities;
- URL and expected archive SHA-256;
- expected cross-prefix and cross architecture;
- detected archive, extraction root, and compiler path;
- compiler version output and, where useful, compiler binary hash;
- probed target triple and a minimal object-file ABI check;
- local-host and QEMU compatibility separately;
- last verification time and result;
- recipes and resolved cells that consume the toolchain.

### Detector providers

Detection should be implemented as small providers with structured results:

- **Configured native detector:** checks exact paths and version markers already declared for native builds.
- **Registry cache detector:** inspects only known managed cache locations, verifies the archive SHA-256, checks the expected prefix, and probes a minimal compiled object.
- **QEMU detector:** checks `qemu-img`, `qemu-system-x86_64`, KVM usability, VM image/ISO readiness, and the Python runtime dependencies used by the runner.
- **Local executor detector:** checks whether the invoking Linux environment can run the pinned compiler and has the fixed adapter's required host utilities. This naturally supports a Distrobox/Toolbx invocation.
- **Analysis detector:** checks Ghidra, Java, PyGhidra, and required language/processor mappings.

Detection should be read-only by default. Preparing a toolchain is a separate explicit operation.

The present disposable `work/` download area is not a good long-term managed inventory because fresh runs can remove it. A future configurable cache/data root should hold verified archives and prepared copies outside disposable work directories. Its exact location and retention policy should be decided with the service layout; cached binaries must remain untracked.

## Requirement resolution and unmet recipes

The key operation is a set difference:

```text
requirements for the resolved plan - usable detected inventory = unmet requirements
```

The service should construct a requirements graph:

```text
campaign/batch/item
  -> recipe
  -> resolved cell
  -> registry toolchain row
  -> target ABI
  -> executor and analysis dependencies
```

Each resolved cell receives one readiness result:

- `ready` — all required inputs and dependencies can execute;
- `download-required` — a pinned artifact is absent but can be fetched;
- `prepare-required` — verified archive is cached but not extracted/validated;
- `blocked` — no reviewed registry match or required dependency exists;
- `incompatible` — the selected executor cannot run the pinned toolchain;
- `missing-dependency` — a required QEMU, host utility, Ghidra, or Java component is absent.

An unmet-recipe check should detect at least:

- a source recipe family or requested variant has no source-capable registry row;
- a requested target ABI has no compatible archive or source candidate;
- a configured native tool path is absent;
- a registry row lacks a required pin, digest, prefix, or architecture value;
- a recipe names an unsupported build adapter;
- `local` was selected but the pinned cross-compiler cannot run in the invoking Linux environment;
- QEMU was selected but QEMU, KVM, or the pinned guest image is unavailable;
- a cached archive has the wrong digest;
- the probed compiler target differs from the registry ABI;
- the resulting binary has no supported Ghidra language mapping.

Archive-only candidates should be checked only for their archive pins and library member. They must remain unaffected by source-executor readiness.

### Alert levels

- **Info:** a pinned download or preparation step is needed; cache is cold; ETA confidence is low.
- **Warning:** local execution is incompatible but QEMU is ready; disk or retention headroom is approaching a limit.
- **Blocking:** no registry match, required configured tool missing, unsupported adapter, no Ghidra mapping, or no usable executor.
- **Integrity/security:** digest mismatch, unexpected compiler identity/target, or an attempt to use an unpinned toolchain.

Alerts should include affected recipes/cells, the structured reason, and a typed remediation. They should not merely say “toolchain missing.” The dashboard should count blocked cells and the recipe catalog should show toolchain coverage and uncovered variants.

## Toolchain preparation workflow

A “prepare requirements” operation should:

1. resolve the reviewed plan without executing builds;
2. calculate its exact pinned prerequisites;
3. inventory the current environment and managed cache;
4. show downloads, extraction size, executor compatibility, and blocking gaps;
5. require confirmation for downloads or cache changes;
6. fetch only registry-pinned URLs and verify digests;
7. extract into an isolated managed directory;
8. verify the expected compiler prefix, version identity, and target ABI;
9. record a toolchain inventory snapshot and verification evidence;
10. mark affected cells ready or retain a structured blocker.

Preparation must never add a registry row, change a recipe, relax a digest, or choose a different compiler automatically.

Possible API shapes are:

```text
GET  /api/toolchains
GET  /api/toolchains/{variant}
GET  /api/readiness?plan={digest}
GET  /api/recipes/{id}/requirements
POST /api/toolchains/{variant}/verify
POST /api/toolchains/{variant}/prepare
POST /api/plans/{digest}/prepare-requirements
```

These endpoints accept identifiers and typed options, never shell commands.

## ETA model

ETA should be based on stage timing history rather than a single global average. Useful dimensions include:

- stage and workflow;
- executor;
- architecture and toolchain variant;
- adapter and recipe/family;
- cache state;
- Ghidra language;
- object or function count where available.

Use rolling medians and percentiles, exposing sample count and confidence. Once a stage starts, combine elapsed time with the historical remaining duration. Batch ETA must simulate the queue across configured worker slots and its critical path; summing every cell duration will overstate parallel runs.

Display an ETA range when evidence is sparse. A cold toolchain download/preparation should appear as a prerequisite stage and influence the estimate.

## Overnight campaigns

An overnight campaign should define:

- start time and optional completion deadline;
- input batch or watched inbox;
- maximum parallel workers;
- executor policy, with QEMU default and local explicitly opted in;
- retry limit and backoff;
- continue-on-error or failure threshold;
- minimum free disk and work/cache limits;
- retention policy;
- allowlisted recipes, toolchains, routes, and treatments;
- allowed network/download window;
- stop-scheduling cutoff and “pause after current cell” control;
- notification policy.

Before arming a campaign, show a preflight summary with planned items/cells, executor routes, pinned toolchains, expected download and disk use, estimated runtime range, projected completion, toolchain blockers, history warnings, and the immutable plan digest.

The scheduled job must consume that reviewed plan digest. It must not silently re-resolve mutable UI selections at start time.

Where policy permits, the service can download and prepare already pinned requirements during an earlier network window, then begin compilation during the build window. It should refuse to arm or start when blocking requirements remain. Automatic preparation does not authorize new registry entries or recipe edits.

Useful controls are:

- arm/start;
- pause scheduling new cells;
- resume;
- cancel queued work;
- cancel an active stage with explicit impact confirmation;
- retry a failed typed stage or cell;
- stop after the current cell;
- reduce worker concurrency when thermal, disk, or load limits are reached.

## Persistence and events

SQLite is likely sufficient for the first version. It can hold campaigns, batches, items, cells, stage attempts, state transitions, timing history, inventory snapshots, alerts, and plan digests. Existing manifests and artifacts remain filesystem evidence and should be referenced rather than copied into the database wholesale.

Every state transition should be an event with timestamp, actor, reason, attempt, and affected identifiers. This supports live updates, recovery after service restart, ETA history, and a defensible audit trail.

Provenance should record:

- resolved recipe and toolchain registry identities;
- archive and source digests;
- executor (`qemu` or `local`);
- adapter and compiler flags;
- target ABI;
- inventory snapshot/verification result;
- route, treatment, profile, and Ghidra identity;
- plan and output digests.

Executor remains routing/provenance, not an FID treatment.

## Safety boundaries

- QEMU remains the source-build default.
- Local source execution is explicit opt-in and warns that it lacks the QEMU isolation boundary.
- No recipe, API caller, or UI field can supply a raw command.
- No runtime override of recipe or toolchain URLs and hashes.
- Derived adapter commands are read-only.
- Detected arbitrary host compilers never replace registry-pinned toolchains.
- Catalog editing is separate from execution and produces reviewable diffs.
- Cache removal requires an exact resolved target and confirmation.
- The existing native zlib/bzip2 route is not changed.
- This design does not require the deferred full Cell/build-dispatch/manifest unification.

## Suggested implementation slices

1. **Run ledger and stage events** — persist the existing execution flow without changing build semantics.
2. **Inventory and requirement engine** — structured detectors, registry coverage, plan readiness, and alerts.
3. **Manual batch queue** — immutable plan digest, worker service, controls, and recovery.
4. **Overview and batch detail UI** — live status, logs, evidence, and toolchain readiness.
5. **Toolchain preparation** — typed verify/download/prepare operations and managed cache policy.
6. **ETA model** — stage timing history, confidence, and parallel queue simulation.
7. **Overnight scheduler** — campaign policy, preflight, cutoffs, notifications, and resource limits.
8. **BSimVis handoff** — open completed outputs in the downstream analyst workspace.

The best first UI milestone is read-only catalog inspection, plan resolution, toolchain readiness, and live run monitoring. That provides immediate operational value without introducing configuration mutation or a new build authority.

## Matrix-first control model

The build matrix should be the foundation of the operator experience. It combines
three related but distinct views of truth:

1. **Desired coverage** — libraries/subjects, platforms/toolchains, and named FID
   sensitivity variants selected in the TOML plan.
2. **Current execution state** — materialized queue entries grouped into batches,
   including queued, leased, running, blocked, complete, and cancelled states.
3. **Artifact inventory** — sealed builds with matching provenance, loose
   `artifact-only` outputs, and genuinely unbuilt cells.

The left column is an ordered list of build subjects. It must show recipe
identity, current batch membership, queue state, and artifact coverage. Selecting
**Provenance** opens the reviewed recipe path, schema, source URL and digest,
adapter, batch, and related immutable identities. Immutable pins are read-only;
later editing should produce a reviewable TOML change and a new resolved plan.

Batch order is the operator-facing priority mechanism. Reordering batches on the
Batches screen changes the effective subject order in the matrix and the order
used to materialize queue entries. The matrix must not maintain a competing
priority value. Within a batch, an explicit strategy chooses between:

- `recipe-then-variant`: finish all selected factor combinations for one subject
  before moving to the next; and
- `variant-then-recipe`: sweep one factor combination across subjects before
  moving to the next combination.

Each materialized entry retains its batch, base cell, exact factor-variant tuple,
and deterministic position. The resolved TOML/JSON captures requested coverage
and initial order; the coordinator owns live queue state. Future machine policy
may reprioritize the queue, but every change must be an event with actor, reason,
old/new position, batch, and resolved plan identity. This allows the GUI to show
machine-controlled scheduling without pretending that the browser is the final
runtime authority.

### Main analyst matrix

The matrix is the application's default window, not a secondary planner. It is
the analyst's high-density view of how the entire factory is progressing.

- Batch groups run vertically from highest/current priority to later batches, so
  the analyst scrolls downward through time and priority.
- Within each batch, library rows are grouped by their current match set. Match
  grouping must distinguish ground truth, candidate matches, reference sets, and
  unresolved/deferred sets without inventing match confidence.
- Library, batch, queue and inventory columns remain sticky on the left.
- Platform/ABI, toolchain identity, code generation, hardening, link/output and
  analysis/recovery groups run horizontally and can collapse independently.
- A collapsed variable group remains as an aggregate crosspoint column rather
  than disappearing, preserving awareness that hidden factors exist.
- Every intersection can be selected per library. Per-matrix
  `factor_variants` in TOML preserves these relationships instead of reducing
  the GUI to a global setting.
- A persistent layer control switches between plan state, artifact inventory,
  and a combined overlay.
- Sealed `built` state requires matching provenance evidence. A loose FIDB is
  `artifact-only`; a completed historical batch is not sufficient to claim an
  artifact is still built and available.
- Queue, cell detail, ETA and authoritative TOML are supporting drill-downs below
  the matrix, not competing primary interfaces.

## Sensitivity catalogue is an open register

The sensitivity catalogue must not present its current row count as the total
number of ways FID output can change. It is a versioned, extensible register of
factors known so far. The GUI should derive counts from the catalogue and show
the catalogue version or digest; it must not hard-code a number such as 23.

The first report audit corrected an important counting error. The sensitivity
CSV contains 38 route-specific comparisons and 23 treatment slugs, but only 16
factor labels: 13 independently varied build factors, two repeatability
controls, and one compiler-configuration × optimisation interaction. The
interaction is not another primitive knob. Function-recovery evidence adds six
named profiles over three routes and three cohorts; profiles are configuration
bundles, not atomic factors.

Normalizing the controls explicitly named by the report produces the current
41-dimension operational baseline:

- 9 build-input and provenance dimensions;
- 11 binary-shaping dimensions;
- 11 analysis and recovery dimensions;
- 4 analysis-environment/tool identity dimensions; and
- 6 truth, matching and admission dimensions.

Only the 13 build factors should be described as independently measured. The
remaining rows are controls, provenance, algorithm policy or safety/evaluation
context. The matrix must show that distinction and keep named recovery profiles
as selectable bundles over separately visible component settings.

Catalogue entries need an evidence/maturity distinction:

- **measured** — independently varied in the sensitivity study;
- **observed control** — held constant or repeated to measure reproducibility;
- **known pipeline control** — the report or implementation identifies the
  control, but it has not yet been independently swept;
- **hypothesis/backlog** — plausible influence that still needs a designed
  experiment before it can drive reference expansion.

These categories should not be collapsed into a claim that all factors have
measured effects. Compound comparisons such as compiler × optimisation are
experiment definitions composed from primitive factors, not another primitive
build knob. Recovery profiles are named bundles and should expose their
component settings as nested factors. Outcome measures such as recovered,
hashable, ambiguous and wrong-library counts describe usefulness and admission
risk; they are not selectable build variables.

The report-backed catalogue is only the first baseline. It must expand as new
platforms, toolchains, build systems, import/recovery controls, FID generation
settings and matching/admission policies are studied. Adding a factor does not
make it executable: a factor may remain visible as an unmet or unmodeled matrix
column until reviewed variants, toolchain support and any required truth model
exist.

## Tier 0: runtime foundations

The highest-priority coverage batch is `batch-000`, **Tier 0 · Runtime
Foundations**. It is an operator priority class for ubiquitous runtime identity,
not a FID treatment and not a claim that every subject is presently runnable.
It starts at position 01 in the batch queue and moves through the same auditable
batch-order mechanism as every other batch.

The initial subject catalogue is grouped as follows:

- Linux C runtimes: glibc, musl, legacy uClibc, and uClibc-ng;
- Windows runtime foundations: UCRT, VCRuntime, MSVC STL/MSVCP, legacy MSVCRT,
  and MinGW-w64 CRT;
- Apple runtime foundations: libSystem, including its Libc, dyld, and
  `libsystem_*` constituents;
- GCC runtimes: libgcc/libsupc++ and libstdc++;
- LLVM runtimes: compiler-rt builtins and libc++/libc++abi/libunwind;
- Android Bionic;
- ubiquitous support libraries: zlib;
- conditional firmware runtimes: newlib and picolibc; and
- language runtime families: Go runtime/stdlib and Rust core/alloc/std.

Startup and ABI objects (`crt1`, `Scrt1`, `rcrt1`, `crti`, `crtn`,
`crtbegin`, `crtend`, and glibc nonshared components) remain nested beneath the
relevant runtime family instead of becoming misleading independent libraries.
The same applies to runtime satellites such as `libm`, pthread, `libdl`,
`librt`, and resolver components.

Readiness must be explicit per subject. At the time this batch was defined,
zlib has a reviewed native recipe and legacy uClibc has one reviewed PowerPC
source route. The toolchain registry also identifies pinned archive candidates
for glibc, musl, and uClibc/uClibc-ng families; those pins are not source-build
recipes and are not built artifacts. The remaining Tier 0 subjects are desired
coverage gaps until their acquisition policy, reviewed recipe, toolchain/SDK,
target route, adapter, and provenance contract exist.

The GUI can materialize only the reviewed Tier 0 cells into its priority queue
draft. Catalogue-only subjects remain visible as blocked intersections and do
not enter `fidb-plan/v1` TOML. That schema expresses executable intent and has no
batch/tier or wishlist type. A later declarative coverage-intent schema should
represent desired, archive-catalogued, source-runnable, and unmet states before
resolution produces executable plan cells. Defined does not mean queued: a
coordinator must accept the resolved plan before entries become submitted,
leased, running, or complete.

## Queue implementation checkpoint

The first local execution slice now uses `plans/priority-queue.toml`
(`fidb-queue/v1`) as the explicit priority authority. `batch_order` is the
ordered list the worker follows; each batch references an immutable
`fidb-plan/v1` request. For first commissioning, the active Tier 0 batch filters
that plan to native zlib and is followed by the native bzip2 baseline. The
reviewed PowerPC matrix remains in its plan but is excluded from this queue;
the separate Mirai baseline is also outside the library-local queue.

`fidb-poc queue sync` resolves those plans into an ignored, host-local SQLite
ledger without executing them. The ledger provides ordered atomic claims,
renewable fenced leases, capped retries, pause/resume state and append-only
events. Blocked cells remain visible but unclaimable, allowing the worker to
continue to later runnable work. Multiple worker processes on `reference-host` can
share this ledger; remote/multiplatform workers need a coordinator API rather
than direct SQLite access.

`fidb-poc queue run` is the typed execution boundary. It refuses a disarmed
queue, creates an isolated attempt root, and re-resolves reviewed authority
before doing work. A successful cell must reach preparation/build, artifact
validation, Ghidra ingest/analysis, FID population and validation, FIDB plus
FIDBF export, atomic provenance sealing, and generation-specific publication.
Recipes and callers still cannot provide raw commands. The commissioning
priority list contains only native zlib and bzip2 cells. PowerPC, QEMU and
malware remain outside it. A `library-local` worker claim is also validated
fail-closed, so a future accidental QEMU or malware queue row cannot be
consumed by this pool. After disarmed resolution review, this narrow queue is
deliberately armed for commissioning with an active lease cap of two, not the
host's 32 hardware-thread count.

The bounded loopback coordinator API and GUI binding now exist. The Python API
exposes health, status, snapshot, events, capability detection, and typed
sync/pause/resume only. A server-side control-panel route forwards the fixed
same-origin browser surface to `127.0.0.1:8765`, so a Mac browser can reach live
data over the control panel's Tailscale address without exposing SQLite or the
API itself. It cannot arm, claim, run, or accept a command. Capability detection
for the commissioning queue reports two immediately ready native library jobs;
the download-required PowerPC source cell is not active in this run.

Repository systemd templates exist for the loopback API and up to four
declared `library-local` worker processes. During the first commissioning run,
the API and two explicit worker instances were installed in the `fidb-operator`
user manager; the workers were stopped and disabled after the queue drained,
while the healthy loopback API remained enabled for inspection. The reviewed
queue cap remains two active leases; move to four only after real per-stage
RSS, duration, disk and thermal evidence.
Sixteen or 32 end-to-end workers are unsafe with four compiler jobs and a Ghidra
JVM per worker, especially because Linux currently exposes about 62 GiB of the
nominal 128 GiB host memory.

Durable timing capture and inspection are now implemented. Every fenced attempt
has typed stage-attempt rows with UTC boundaries, worker-monotonic duration,
process/child CPU and peak RSS measurements, stage metrics, retries, failures,
explicit skips, and coordinator-wall-clock interruption recovery. Timing also
travels in the sealed execution result. The bounded API and GUI expose active
stage clocks, recent evidence, p50/p90 stage and workflow distributions, queue
wait basis, and a reciprocal successful-final-attempt service-rate proxy. That
proxy excludes retry work, queue/idle time and worker concurrency and is not
labelled as observed whole-factory throughput. Interrupted/estimated spans
never enter worker-monotonic percentiles, and the GUI deliberately says
**Collecting evidence** while the ledger has no real samples. ETA is still null until a
matching, parallelism-aware estimator has sufficient history.

Still missing are that ETA estimator, schedule windows and cutoff policy,
notifications, shared locked toolchain caching, stage-specific resource gates,
worker registration/telemetry, an authenticated remote-worker API, and the
deferred common manifest unification.

## First overnight commissioning decision

The first unattended exercise is a deliberately small **native-library smoke
run**, not a claim that the factory is ready for production overnight use.  Its
purpose is to validate the exact queue-worker boundary, isolated attempts,
Ghidra ingestion and analysis, FID population, FIDB/FIDBF export, sealed
publication, durable timing, and automatic progression through TOML priority
order on the real `reference-host` host.

The pre-commissioning audit found:

- `plans/priority-queue.toml` was disarmed with three active queued cells and no
  attempts or timing samples;
- native zlib and bzip2 were immediately ready under the reviewed
  `linux-x86_64-gnu-gcc` route;
- the explicit-local PowerPC uClibc cell required acquisition of its pinned
  cross-toolchain and had not yet exercised the managed download path;
- Ghidra 12.1.2, Java 21, PyGhidra, GCC, binutils, make and patch were present;
- the repository contained reviewed API and worker unit templates, but no user
  units or operator environment had been installed or enabled;
- no API, worker, Ghidra or build process was running; and
- host capacity was ample for a two-worker smoke, but there was no evidence for
  scaling beyond the existing `max_workers = 2` cap.

The commissioning scope therefore excludes PowerPC, QEMU and malware.  The
active Tier 0 batch selects only its reviewed native zlib matrix, followed by
the native bzip2 batch.  The PowerPC plan remains preserved as desired reviewed

## Next steps: lane database buildout

Treat a lane as the analyst-facing deployment boundary for a device/platform
family, not as a single bitness or Ghidra language. Examples include
`linux-x86`, `windows-x86`, `macos-apple-silicon`, `android-arm`,
`android-x86`, and `ios-arm`. A user installs or opens one lane database; the
system must inspect the binary and select an exact internal sublane without
requiring the analyst to identify its architecture. Thus `linux-x86` contains
both ELF x86-32 and ELF x86-64, `windows-x86` contains PE x86 and x86-64, and
the Apple-Silicon lane can describe native ARM slices, universal binaries, and
supported translated execution separately.

The internal sublane is the query-compatibility and semantic-deduplication
boundary. It retains exact format, ISA, bitness, endianness, OS/ABI, Ghidra
`LanguageID`, Ghidra `CompilerSpecID`, FID algorithm and analysis-policy
version. Compiler family/version, treatment, library and release are occurrence
provenance within a sublane; they do not create user-visible databases. If a
binary does not carry enough evidence to choose one OS/ABI interpretation, the
resolver should query the small applicable candidate set and report the
ambiguity rather than ask the analyst to choose an architecture.

Build the system in the following reviewable slices:

1. Add a declarative, versioned lane registry describing each broad lane, its
   supported internal sublanes, binary selectors, cross-runnable cases and
   unresolved coverage. Initially claim only sublanes backed by qualified
   routes; for example, the existing OpenSSL run supplies Linux x86-64 evidence
   but not the x86-32 half required to call `linux-x86` complete.
2. Make all signature, overlap and marginal-coverage calculations sublane
   aware. The canonical signature identity must include the sublane and FID
   policy namespace in addition to the full hash, specific hash and size
   fields. Add regression tests proving equal numeric hashes from incompatible
   sublanes are never semantically collapsed.
3. Implement an immutable raw lane-generation schema, initially as a portable
   SQLite database. Represent lane generations, sublanes, libraries, releases,
   build variants, every raw signature observation, function relationships and
   generated native-projection state. The raw generation must not deduplicate:
   even byte-for-byte identical input rows remain independently inspectable.
4. Build a read-only lane compiler and dry-run report over the completed
   OpenSSL evidence. It should calculate per-sublane uniqueness, occurrence
   fan-out, collisions/ambiguous ownership, projected pack size and provenance
   completeness without altering or deleting the source cell artifacts.
5. Keep semantic deduplication as a separate, inspectable compact-copy
   experiment. It must be dry-run by default, print the exact key and SQL,
   refuse in-place replacement, retain one occurrence edge for every raw row,
   and leave all compact signatures unreviewed until ecological validation.
6. Extend worker output into immutable lane-admission bundles. The current
   JSONL signature ledgers are adequate for overlap measurement but do not
   contain every relationship required for a faithful native Ghidra database.
   Future bundles must retain the analysed-program/object input or export the
   complete function and relationship evidence needed to reconstruct and audit
   the projection.
7. Implement the native Ghidra projection builder. Populate a consolidated
   writable `.fidb` from admitted programs for each exact sublane, validate it,
   then emit the read-only `.fidbf` used for matching. Do not assume per-cell
   databases can be concatenated. Compare results against the original cell
   databases and require query-equivalence or an explained, reviewed delta.
8. Publish one checksummed lane pack, for example
   `linux-x86-c-v1.fidbpack.tar.zst`. It may expand internally to
   `manifest.toml`, `catalog.sqlite`, exact `.fidbf` projection shards and
   checksums, but remains one installable/versioned database to the analyst.
   Publish immutable generations and activate or roll back with an atomic
   generation pointer rather than mutating an active pack.
9. Add the automatic BSimVis/Ghidra resolver. It inspects the binary and Ghidra
   program metadata, selects applicable projection shards, performs native FID
   matching, joins matches to canonical provenance, and records the lane,
   generation, sublane, evidence and ambiguity used for every decision.
10. Implement reversible BSimVis handling: tag matches first, preserve original
   functions and features, and construct boilerplate-ablated views only from a
   versioned policy. Shared-owner, collision-suspect and weak matches remain
   visible and must not be silently attributed to one library.
11. Expose lane coverage, missing sublanes, pack generations, storage,
    signature fan-out, ambiguity, collision review, query validation and
    ecological-validation state in the GUI. The GUI explains and operates on
    the reviewed registry and manifests; it does not become a second source of
    lane truth.
12. Run the ecological validation below in tag-only/shadow mode. A populated
    and technically queryable pack is not operationally releasable until its
    false-positive, recall and ambiguity results satisfy reviewed thresholds
    on independent real binaries.

The product contract is: one broad database for the analyst, exact internal
sublanes for safe matching and deduplication, and lossless occurrence
provenance for every compiler and treatment observation.

## Continuous machine-led cohort validation

Machine validation is an ongoing construction check, not the final ecological
claim. After each complete cohort of ten library families, freeze a uniformly
random, reproducible five/five family split. Keep every release of a family in
one fold, commit the seed, algorithm, sorted input IDs and resulting assignment
before observing match results, and never reroll an inconvenient split. The
first frozen cohort is `c-top10-cohort-001` in
`validation/machine-validation.toml`.

For every executable target/compiler/treatment identity in the cohort width,
build two non-executed composite programs: one forcing all five fold-A static
libraries into the link and one doing the same for fold B. Preserve an
unstripped truth copy and link map, then create the stripped query copy. The
validation runner should query each composite against an owner-labelled index
in three ways:

- its correct fold with the exact build identity withheld, measuring genuine
  compiler/variant generalisation rather than a trivial self-match;
- the opposite fold, measuring negative attribution and ambiguity; and
- the complete candidate database, measuring owner competition against every
  other indexed library without an unnecessary all-pairs binary comparison.

Run a small exact-inclusion canary separately as a pipeline sanity check. A
cross-fold hit is not automatically a false positive: shared source,
dependencies, compiler boilerplate and genuinely indistinguishable functions
must be reported as ambiguous/shared until stronger provenance adjudicates
them. Record correct-library recovery, cross-fold misattribution, ambiguity,
leave-one-compiler/variant-out recall, marginal coverage by factor, regressions,
wall time, peak/continuous memory, scratch and retained storage.

This is a separate `validation-run` batch type. Its materialiser is disarmed
and fail-closed: it may be inspected now, but must refuse to emit runnable work
until all ten libraries have sealed evidence for every applicable execution
exact width identity. The present 222 identities are a baseline, not a fixed
ceiling: adding a route, compiler version, treatment or other executable width
must automatically increase the cohort requirement and block validation until
that evidence exists. Eligible cohorts are materialised and registered with the
validation scheduler automatically, without rewriting the active production
priority queue. The first generated run remains claim-blocked until its
post-cohort canary validates the new composite executor; later validated
cohorts can chain automatically in the configured scheduler window. At the
present width the first run will comprise
222 work units, 444 composite programs and 1,332 primary query projections.
Existing width completion is the admission
gate; validation composites are rebuilt from the reviewed, pinned recipes
because the earlier OpenSSL evidence did not consistently retain reusable
static archives and an independent rebuild is the cleaner experiment.

One frozen five/five split is the primary ongoing check. Add another seeded
split only when a result is ambiguous or when rotation sensitivity itself is a
research question; do not multiply the routine run by every possible split.
The planning estimate is deliberately broad until the first measured run:
roughly 15--35 hours on `reference-host` (central estimate 25 hours), 60--80 GiB safe
RAM budget, 75--100 GiB scratch headroom, and approximately 17--65 GiB of raw
retained evidence depending on object retention. Compact reports should be
well below 1 GiB. Replace these assumptions with machine evidence after the
first eligible run.

Use ten-library cohorts by default, but do not discard a final remainder when
the dataset size is not divisible by ten. A final 2--9-library cohort requires
an explicit TOML override and written justification. Allocate it with the same
seeded ranking and the most balanced possible split; an odd remainder therefore
has one extra family in fold B. The GUI must display this exception and its
reason so a short cohort cannot be mistaken for an ordinary validation block.

The GUI must expose cohort completion, the frozen folds, exact-width progress,
eligibility blockers, validation stages, resource assumptions and the
separation from ecological validation. Matrix visibility is a status projection
only; TOML remains authority. Once reports exist it must put a clearly defined
TP/FP/TN/FN decision matrix at summary level. False-positive collisions and
false-negative misses require an expandable row-level ledger with the precise
library/function, route, compiler, treatment, signature, competing owner and
evidence locator; aggregate rates alone are not diagnosable.

## Pre-deployment ecological validation

The implementation authority is `validation/ecological-validation.toml` and
the control panel has a distinct Ecological validation workflow. An imported
file is preserved and SHA-256 pinned, is never executed, and must resolve from
binary format/ISA/bitness/endianness plus an explicit platform hint where the
file cannot distinguish Linux from Android. A check selects the latest
compatible lane generation and queries its entire library-owner population;
cross-lane negatives are invalid because the signatures are not query
compatible.

The defensible confusion-matrix unit is imported-binary × corpus-library
presence, not guessed function ownership. Expected-present libraries produce
TP or FN decisions. Explicit expected-absent libraries—and all unlisted corpus
owners only when the analyst marks truth complete—produce FP or TN decisions.
Incomplete truth remains unlabelled. Collisions and misses retain exact
function/signature/build/database evidence for human review.

This formal validation is performed only after the intended final dataset,
lane generation and matching policy have been frozen. It is distinct from the
continuous synthetic five/five cohort checks above. No lane database should be
approved for analyst use merely because it matches
the libraries from which it was built. Before enabling boilerplate ablation,
run it in tag-only or shadow mode against a separate, ecologically realistic
corpus of complete binaries. The corpus should include real operating-system
and application executables, shared objects, statically and dynamically linked
programs, stripped and unstripped samples, and both known-positive and
known-negative controls. None of these validation binaries should have been
used to construct the lane database.

Adjudicate sampled matches against stronger evidence such as package and build
provenance, symbols or debug information where available, source-correlated
builds, raw/normalised instructions, p-code, and call relationships. In
particular, oversample short functions, signatures with many possible owners,
cross-library signatures, and the collision-like population where different
object/function identities share the same FID signature. Distinguish at least:

- a true match to code derived from the claimed library;
- structurally identical/common boilerplate for which unique ownership cannot
  be claimed;
- a useful but ambiguous match that must not drive automatic ablation; and
- a true false positive: unrelated code incorrectly attributed to the library.

Measure results separately for every query-compatible sublane and published
lane generation. Report precision, false positives per million analysed
functions, binaries containing at least one false positive, recall on the
known-positive controls, ambiguity/abstention rate, and the effect of each
matching or ablation threshold. Preserve the validation corpus manifest,
digests, match evidence and adjudications so the result is reproducible and
can be rerun after Ghidra, policy or database changes.

Automatic masking remains disabled until reviewed acceptance thresholds have
been met. Collision-prone or unresolved signatures should be quarantined or
retained as evidence-only matches; BSimVis should tag them without removing
them from the analyst's residual view. This ecological validation is the gate
between a technically populated lane pack and a lane pack safe for operational
boilerplate ablation.

## Noisy-hash trust management

Repeated collision evidence is a first-class validation output. The control
panel therefore has one Validation group with separate Machine validation,
Ecological validation and Hash discrimination pages. The existing noisy-hash
ledger is the collision-review section of Hash discrimination rather than a
competing model. The matrix shows their gates at summary level; detailed
evidence and decisions stay on those pages so the matrix remains glanceable.

The noisy-hash compiler reads both report families and groups a signature only
within its query-compatible sublane using the complete FID tuple. A single
collision is a candidate. The initial reviewed rule requires three collision
observations across at least two distinct runs before calling it confirmed
noisy, while two distinct affected owners raise the risk marker. Repeated
ambiguity is evidence requiring review, not by itself proof of a false-positive
hash: common functions, compiler scaffolding and shared source remain plausible
explanations.

An operator can record `observe`, `quarantine`, `reviewed-shared` or `cleared`.
Every choice requires a reason and becomes an auditable TOML file with the
source ledger digest. Existing raw observations, compact generations and
validation reports remain immutable. Quarantine applies only when constructing
a later admission generation; until the lane compiler actually consumes and
records these decisions, the GUI must describe it as a forward contract rather
than claiming the current corpus was filtered. This separation lets the trust
policy be revised or rolled back without destroying evidence.

## Learned hash discrimination

The validation workspace must progress beyond a threshold-based noisy-hash
list into a learned, explainable estimate of how strongly each compatible FID
signature distinguishes library provenance. The analyst-facing feature is
**Hash Discrimination** and its primary measure is the **Hash Discrimination
Index (HDI)** on a 0--100 scale, where higher means more discriminative. Noise
risk, evidence sufficiency and reason classification remain separate outputs;
noise risk is not assumed to be the mathematical inverse of HDI.

The initial implementation is deliberately a visual and authority skeleton.
Before C10 it shows the required corpus inputs, readiness blockers, treatment
arms and planned model generations, but uses unavailable markers rather than
inventing measurements. The scoring compiler later consumes all-signature
corpus denominators as well as machine and ecological outcomes. It must not
learn only from already-reported collisions.

Counts are hierarchical: distinct library families precede releases, routes,
compiler versions and treatments. Build-width observations measure stability
but do not masquerade as independent owners. Scores are conditional on the
complete FID signature, compatible query sublane, candidate owner or resolution
level, corpus generation and model generation.

The frozen ablation compares unweighted FID, exclusion, down-weighting and
context-required retention. A weak signature may support a distinctive
combination without independently driving attribution. Results distinguish
unique provenance, family/shared-code evidence, ambiguity, abstention and
incorrect confident attribution. Machine validation supports development;
held-out ecological validation remains the final release gate.

The complete concept, generation history, rollback boundary and present-data
limitations are maintained in `docs/validation/hash-discrimination.md`. The existing noisy-hash
TOML dispositions remain an auditable human layer and are never overwritten by
the learned model.

The page must always explain its calculation and reproducibility rather than
showing an unexplained score. It renders both component equations and weights
from `validation/hash-discrimination.toml`, defines the family-level
denominators and beta smoothing, and labels the formula provisional until C10
ablation. It also exposes the algorithm ID, authority digest, deterministic
ordering, arithmetic/rounding rules, source-digest policy, required Git
revision and immutable publication policy. A future score row without those
generation pins is invalid evidence.

### Single-hash population observatory

Controlled TP/FP/TN/FN decisions use the complete compatible FID signature:
full hash, specific hash, specific additional size and code-unit size. The
full and specific hashes are also projected independently to answer a narrower
question: how much owner ambiguity would each component create on its own?
The complete tuple is a composite identity, not a third independent hashing
algorithm. Component-level sharing is descriptive ambiguity and must not be
reported as an actual FID false positive.

Every measured validation run preserves full-only, specific-only and complete
population distributions, the owner list for each multi-owner value, the
libraries carrying those values, and the component/owner cases made unique by
the complete tuple. Distinct library-release owners are the primary prevalence
denominator. Build observations remain a separate width-sensitive diagnostic
so wide compiler/treatment coverage does not masquerade as additional library
diversity.

The Hash discrimination page is also the validation observatory. Its primary
visual order is measured outcomes, run selection, hash-type comparison,
prevalence tail, hash/owner drill-down and per-library burden; future HDI model
controls follow those results. It supports both an overview across immutable
batches and a selected-run view. Trend points retain validation ID, run ID,
method digest, report digest and source-evidence digest. Normal refreshes read
bounded JSON reports rather than opening every SQLite evidence file.

The canonical method is `validation/machine-validation-hash-method.toml`.
Changing its identity, denominators or classification rules creates a new
version. The analyser accepts any two non-empty disjoint frozen folds rather
than hardcoding C10, so the same machinery applies to C20/C30 and later
languages without introducing batch-specific scientific logic.

The validation manifest owns one required `hash-discrimination` postprocess
job after its build/analysis units. It performs threshold-free classification,
full/specific/complete population analysis, incremental corpus admission,
selected-backend exact lookup, immutable report publication and retention.
These are batch stages, not an operator-memory follow-up.

Treat machine FN as conditional on the validation construct. References are
per-library archive functions; queries are functions recovered from linked
five-library composites. The C10 architecture dependence—about 17% FN on
Linux x86-64 versus about 90% on MIPS32 BE—is evidence against interpreting
the 45.66% aggregate as intrinsic FID recall. Preserve the raw number, surface
route/treatment/library strata, and require an archive-to-executable control
before making a recall claim.

GPU acceleration is restricted to exact lookup over already-generated packed
hash keys. The qualified C10 WGPU probe was 3.31× the CPU packed probe with
zero mismatches; generation-keyed packing caches remove the measured 8.11 s
repacking cost on reuse. `performance/hash-analysis.toml` exposes auto/GPU/CPU
selection and mandatory CPU fallback. Never extend this switch to compilation,
linking, Ghidra analysis or FID generation without a separate scientific
design and equivalence authority.

therefore 6.784 hours: 43.8% constructing validation binaries and 56.2%
preparing and querying them. The historical composite build actually occupied
4.809 hours of active wall time because its interrupted sessions did not keep
four workers continuously occupied; do not use that figure as the clean
four-worker projection.

Only 0.289 of the projected 3.812 query-stage wall hours was WGPU matching.
The remaining 3.523 hours was query preparation, classification and evidence
publication, dominated by Ghidra relationship-evidence backfill. Every fresh
case sampled by that projection used `new-backfill`. One already sealed
relationship-evidence case completed in 11.518 seconds, versus a 123.64-second
mean for the fresh first-pass cases. That single hot-path observation is not a
representative benchmark, but it confirms that GPU lookup is not the cause of
the query stage exceeding composite construction.

This is duplicated analysis, not an inherent FID-validation cost. Composite
construction already calls Ghidra `analyze_target` and exports
`query-signatures.jsonl`, but the original run did not seal that export as
relationship-complete evidence while the analysed project was open. The
compact matcher must consequently analyse each executable again before it can
query the candidate index.

Before C20 composite construction, make the query export a reusable superset
output of the same canonical Ghidra analysis:

1. Export one relationship-complete `query-signatures.jsonl` before deleting
   the temporary Ghidra project.
2. Seal its schema, roles (`exact-signatures` and
   `fid-relationship-evidence`), analysis-policy identity, byte count and
   SHA-256 digest in the fold result.
3. Make routine detector validation consume only sealed relationship evidence
   and fail closed when it is missing.
4. Keep analysis backfill as an explicit, resumable migration/recovery mode;
   never hide it inside normal query timing.
5. Report composite construction, relationship export, candidate lookup,
   classification and publication as separate timing stages.

The provisional post-change envelope is 3.0--3.3 hours for composite
construction plus both exports and 0.3--0.7 hours for matching and
classification: about 3.3--4.0 hours for a clean C10 cycle. This is a target to
qualify, not measured performance. Replace both projections with terminal
evidence after the current full run and the fused-export implementation have
completed.

### Next implementation: decoupled relationship and scoring pipeline

After eliminating the duplicate analysis above, the next throughput experiment
is stage overlap. The current compact campaign is scientifically valid but
schedules each case synchronously inside one worker:

```text
Ghidra query-relationship export
  -> compact candidate enumeration and WGPU scoring
  -> owner classification and evidence publication
  -> next case
```

A representative large case spent about 162 of 185 seconds producing
relationship-complete query evidence, about 18 seconds in compact matching and
about five seconds classifying and publishing. Four similarly balanced workers
can therefore synchronise their long CPU phases and short GPU bursts, leaving
the GPU idle between bursts and preventing each worker from preparing its next
case while its current case is being scored.

Implement and measure the following without changing FID generation, matching
semantics, truth attribution or evidence identities:

1. Make relationship export an explicit resumable producer stage. Persist and
   digest-bind its relationship-complete `query-signatures.jsonl` before
   admitting scoring work.
2. Feed sealed relationship evidence through a bounded, inspectable work queue
   with backpressure; a crash or pause must resume at a sealed stage boundary.
3. Run a separately sized Ghidra producer pool. Benchmark 4, 6 and 8 producers
   on `reference-host`, recording cases/hour, functions/hour, peak RSS, CPU time,
   temperature and failure rate rather than selecting by core utilisation.
4. Run one long-lived WGPU scoring service. Reuse its adapter, device, compiled
   shader pipelines and bounded buffers instead of invoking independent WGPU
   helpers from four campaign processes.
5. Batch candidate rows across ready cases where this does not change case and
   function identity. Preserve deterministic demultiplexing into the original
   per-case decision receipts.
6. Move owner classification and evidence writing into a bounded downstream
   CPU stage so relationship producers and the GPU can continue concurrently.
7. Record queue depth, stage residence time, GPU duty cycle, transfer bytes,
   dispatch count and backend/fallback identity in the Performance page and
   immutable terminal report.
8. Compare the staged implementation with the current canonical implementation
   over the same retained C10 relationship evidence. Require identical owner
   decisions, confusion matrices and per-hash observations before promotion.
9. Keep the current synchronous path as a selectable fallback until the staged
   path passes equivalence, interruption/recovery and bounded-memory tests.
10. Enforce the fused-export prerequisite for every future source-validation
    cohort so a detector-validation campaign cannot silently fall back to a
    second Ghidra analysis.

Pipeline overlap alone can remove only the roughly 10–15% of current large-case
time spent outside relationship export. The larger expected gains come from
avoiding repeat backfill, safely increasing producer concurrency, and reusing
GPU state. Benchmark these effects separately so a faster cached rerun is not
mistaken for an orchestration improvement.

## Integrated cohort validation lifecycle — 2026-09-07

Every future width cohort now inherits the reviewed lifecycle in
`validation/cohort-lifecycle.toml`. A scientific cohort and an execution block
are different units: the former fixes subjects, seed, folds, exact width and
report identity; the latter is only a resumable scheduler slice. Never reroll
or reinterpret a cohort because it crosses an execution window.

The deterministic five/five experiment did not change. Each exact
route/treatment identity still produces fold A and fold B composites. Its
primary TP/FP/TN/FN matrix compares a present fold with the withheld fold. A
second, separately reported incremental query compares newly admitted hashes
with the cumulative corpus for prevalence, ambiguity and hash-discrimination
evidence. That cumulative result must never change the primary fold
denominators.

Future folds seal one relationship-complete `query-signatures.jsonl` under the
`fidb-integrated-query-evidence/v1` contract. It serves both exact-signature
and FID-relationship consumers, eliminating the second routine Ghidra pass.
Integrated matching fails closed if the schema, roles, analysis policy, byte
count or digest do not match. Historical C10 evidence remains a named legacy
retrofit and may use only the explicit digest-bound backfill path.

`validation/cohorts.toml` binds C11–20 and C21–30 to exact reviewed source
packs, width batches and independent deterministic seeds. These cohorts are
planned and disarmed until complete width evidence is sealed. Later C80 rows
remain structural until screening freezes their identities. Source and recipe
work may proceed one cohort ahead, but at most one completed unvalidated width
cohort may exist. A failed validation pauses admission of the next width
cohort. Validation, hash discrimination and retention must all complete before
corpus-admission review; automatic corpus admission remains disabled until a
separate threshold authority is reviewed.

The initial projected saving is 444 Ghidra analyses per ordinary ten-library
cohort: 888 analyses in the historical two-pass design become 444 fused
analyses. The 3.3–4.0 hour clean-cohort envelope remains a projection until a
future integrated cohort produces terminal timing evidence.

The live legacy C10 pass subsequently exposed intermittent Ghidra reopen
failures for a missing temporary `~journal.dat`. The shared analysis/export
helper now retries only that fingerprint, rebuilding the disposable project
once from the same immutable binary and policy. It records whether the retry
was used and fails closed for all other exceptions. The evidence-preserving
campaign resume path archives the prior concise failure and skips every sealed
case, so a retry does not erase or recompute successful results.
